# SecurityInsight ServiceNow test pack: how to test

This pack lets your ServiceNow developers build and approve the SecurityInsight integration before SecurityInsight runs against your instance. Every row is fictional demo data (contoso.test, fake ids). Times are UTC.

SecurityInsight writes nothing in ServiceNow by default. It delivers rows to staging, and your import set, transform map / IntegrationHub ETL, IRE and Vulnerability Response transform make every change.

## What is in the pack

| File | What it is |
|---|---|
| `sql/vImportBatch.csv` | Batches (the control row), as a JDBC data source reads the view snowstage.vImportBatch |
| `sql/vImportCi.csv` | Configuration items, as a JDBC data source reads the view snowstage.vImportCi |
| `sql/vImportCiKeyValue.csv` | Tags (key-values), as a JDBC data source reads the view snowstage.vImportCiKeyValue |
| `sql/vImportCiRelation.csv` | Relations, as a JDBC data source reads the view snowstage.vImportCiRelation |
| `sql/vProposedCi.csv` | Proposed CIs (a report, nothing is created), as a JDBC data source reads the view snowstage.vProposedCi |
| `sql/vImportVulnerableItem.csv` | Vulnerable items (every security recommendation), as a JDBC data source reads the view snowstage.vImportVulnerableItem |
| `rest/u_si_ci_import.insertMultiple.json` | Configuration items (Import Set push), the body SecurityInsight sends: POST /api/now/import/u_si_ci_import/insertMultiple |
| `rest/u_si_vuln_import.insertMultiple.json` | Vulnerable items (Import Set push), the body SecurityInsight sends: POST /api/now/import/u_si_vuln_import/insertMultiple |
| `rest/u_si_staging_status.json` | Staging status table (SecurityInsight staging status): when a batch is complete, the body SecurityInsight sends: POST /api/now/import/u_si_staging_status |
| `columns.csv` | Every column: type, always or when known, meaning, the ServiceNow field it maps to, an example |
| `servicenow-test-pack.json` | Everything above in one file, with the case of every row |

## Steps

1. **Register the discovery source.** Add `SecurityInsight` as a choice on `cmdb_ci.discovery_source`. IRE refuses a payload from an unregistered source.
2. **Create the staging tables** (import set tables extending `sys_import_set_row`). Suggested names: `u_si_ci_import` (`sql/vImportCi.csv`), `u_si_ci_keyvalue_import` (`sql/vImportCiKeyValue.csv`), `u_si_ci_relation_import` (`sql/vImportCiRelation.csv`), `u_si_vuln_import` (`sql/vImportVulnerableItem.csv`). The column NAMES must be exactly the files' names (`u_si_correlation_id`, ...): both channels address a column by its name. Every column is a string at least as long as `columns.csv` gives it -- `u_si_correlation_id` 400 (real keys are longer than 150 characters), `u_vulnerability` 100; a 40-character default truncates. If you create them with *System Import Sets > Load Data*, check the names and lengths it made against `columns.csv`.
3. **Import Set push only: map by column NAME.** For each staging table add a *REST Insert Multiple* record (`sys_rest_insert_multiple`, source table = the staging table) with a *Column mappings* row (type `application/json`, column mapping = *Column name*). Without it `/insertMultiple` maps the keys to the column LABELS, and on a table whose labels are not the names every row lands with every column empty -- 200 OK, nothing transformed (measured on the Brazil release, 2026-10-06). SecurityInsight reads the first batch back and stops with that message when it happens. The insert is asynchronous by default; the same record can make it synchronous.
4. **Identification and reconciliation BEFORE the first transform.** Keep your identification rules first and add `u_si_correlation_id` only as the last identifier entry. Add the reconciliation rules too: SecurityInsight authoritative for its own attributes (tier, tier reason, exposure, last seen, source run, state), the lowest-priority source for everything else. Do it before any SecurityInsight row is transformed: IRE lets the source that last wrote an attribute keep writing it, so an attribute SecurityInsight wrote while the rule was missing stays writable by it until its owner writes it again (measured). IRE also sets `discovery_source` and `last_discovered` to the last source that touched a CI, so `discovery_source = SecurityInsight` says who updated it last, not who owns it.
5. **Build the transform maps.** A classic transform map has no *use IRE* switch: an *onBefore* script hands the row to IRE and then ignores it (`ignore = true`) -- ServiceNow's `CMDBTransformUtil` (`setDataSource('SecurityInsight')`, one target class per map), or, for the per-row class in `u_proposed_class`, `SNC.IdentificationEngineScriptableApi.createOrUpdateCIEnhanced('SecurityInsight', payload, {})` -- or IntegrationHub ETL. Never set `error = true` in a transform script: it aborts the rest of the import set. An asset-keyed row (`u_id_source = asset`, no ledger id yet): `identifyCI` first, and create nothing when IRE would insert. A push sends every row on every run: skip a row whose `u_row_hash` equals the hash kept on the CI (for example in a `u_si_row_hash` field), or every CI is updated on every run. Map the identifiers as `columns.csv` says; key-values to `cmdb_key_value` (a Defender tag is a key without a value), relations to `cmdb_rel_ci` (the child by its CI key, else by `object_id` in the class of `u_child_class_hint`). Vulnerabilities through your Vulnerability Response transform, coalescing on `u_source_record_id` when it is present (it never changes for one finding), else on `u_si_correlation_id` + `u_vulnerability`; the CI is the one whose `u_si_correlation_id` is the row's -- the CI rows and the vulnerability rows carry the same key.
6. **Dependent and new classes.** `cmdb_ci_vm_instance` is a DEPENDENT class (hosted on a logical datacenter, itself hosted on a cloud account); the hand-off does not carry that chain, so IRE answers `MISSING_DEPENDENCY` and inserts nothing. Match the VM the connector that owns it (Service Graph / Cloud Discovery) created, by class and `object_id` (the vmId), and set only the SecurityInsight attributes on it -- through IRE with the owner's hosting chain in the payload it would also stamp the datacenter and the account as updated by SecurityInsight. A new class for Azure resources extends `cmdb_ci_vm_object`, so it inherits `object_id` (a custom column on a class directly under `cmdb_ci` becomes `u_object_id`); identities identify on `u_entra_object_id`. Children SecurityInsight does not send (disks, network interfaces) must exist from another source for a relation to land; a user-assigned managed identity is a child by its ARM id, which no Entra identity class carries.
7. **Every security recommendation is a vulnerability.** A row whose `u_finding_type` is `cve` maps to the NVD entry of its CVE; any other type (a Defender for Cloud recommendation, a Defender security configuration, an identity finding, an attack path, an exposure) maps to a third-party entry with `u_vulnerability` as its id and `u_title` as its name.
8. **Dates.** The SQL views give a datetime (UTC). The Import Set rows give every date as `yyyy-MM-dd HH:mm:ss` in UTC -- ServiceNow's own date-time format, so a field map needs no date format.
9. **Run the transforms** on the loaded sample rows and compare with the expected results below.
10. **Then connect the real feed.** SQL channel: a JDBC data source on your MID Server, *Specific SQL* `SELECT * FROM snowstage.vImportCi WHERE u_changed_at > ?` (one data source per view). REST channel: SecurityInsight posts the `rest/` bodies to your staging tables -- CI and vulnerability rows only; tags and relations reach ServiceNow through the SQL channel.

Its Defender tag is in vImportCiKeyValue. | Your transform/IRE identifies it by serial_number or name + dns_domain. With creation allowed for computers, IRE creates a cmdb_ci_computer with discovery source SecurityInsight; otherwise it stays in the proposed report. |
| Changed CI | SRV-APP01 moved from tier 2 to tier 1 and gained a criticality and a data sensitivity. Its u_row_hash changed, so u_changed_at moved to this run and a delta import picks it up. | IRE matches the existing server (serial number) and updates u_si_tier and u_si_tier_reason. Attributes another source owns are not overwritten (SecurityInsight is the lowest-priority source). |
| Unchanged CI (with a removed tag and a removed relation) | vm-demo-app01 did not change: u_changed_at keeps its older value, so a delta import skips the CI row. Its costcenter tag and its second data disk are gone: those rows are present with u_state = removed and u_changed_at = this run. Its u_object_id is the VM id (vmId), the key Service Graph / Cloud Discovery identify a VM by. | No CI update. The transform removes (or flags) the costcenter key-value and the relation to the detached disk. |
| New Azure resource no CMDB CI matches | kv-demo-secrets (a Key Vault, tier 0, exposed to the internet) is new and unmatched: in vImportCi with the proposed class u_cmdb_ci_azure_key_vault, and in vProposedCi with its evidence. | Identified by object_id. If your instance has no class for Key Vaults, the transform maps it to your fallback class or leaves it in the report. |
| Identity | sp-demo-payroll-sync (a service principal, tier 0). Identities are handed over too, with the proposed class u_cmdb_ci_entra_service_principal and u_id_source like every other row. Whether a CMDB CI matches is unknown, so it is listed in vProposedCi. | Your decision: create it in an Entra identity class (identified by object_id), or ignore identities in the transform. |
| No ledger id yet | DESKTOP-DEMO9's correlation id is still provisional, so its key is its own asset id (u_id_source = asset): a provisional id moves and is never a key. vProposedCi says it must not be created from yet. | The transform skips creating a CI from an asset-keyed row (it may still update a CI it already matches). |
| CI SecurityInsight no longer sees (in its grace period) | LAPTOP-0077 (a client PC) was last seen 8 days ago -- its owner is on holiday. Its row stays in the hand-off with u_si_state = not-seen and its last u_last_seen; u_changed_at moved to this run because the state changed, so a delta import picks it up. It is retired only after the grace period of a client PC (30 days by default, a Pro setting per kind) unless it is seen again. Its open vulnerability stays open (held). | Your transform decides what not-seen means (usually nothing yet, or a flag). Nothing is retired or deleted. |
| CI SecurityInsight retired after its grace period | SRV-OLD02 (a server) was last seen 31 days ago -- past the 30-day grace period of a server -- so SecurityInsight retired it this run: u_si_state = retired, u_changed_at = this run. Its open vulnerabilities close as AssetRetired. If it is seen again it becomes active again and its findings reopen. | Your transform decides: a flag, a task for your CMDB team, or install_status. SecurityInsight never retires or deletes a CI in ServiceNow, and never touches records it did not send. |
| Vulnerability opened | CVE-2099-10001 on LAPTOP-0142, new this run: u_state = Open (REST: u_action = new). Its u_si_correlation_id is the CI row's key, so the CI resolves directly. | Your Vulnerability Response transform creates a vulnerable item linked to the CI. |
| Vulnerability still reported | CVE-2099-10002 on SRV-APP01, still reported: u_last_seen moved (REST: u_action = update). | The vulnerable item is updated (last_found); no second item is created. |
| Vulnerability reopened | CVE-2099-10003 on SRV-APP01 was closed by an engineer, but SecurityInsight still reports it: the row says Open (REST: u_action = update). | Your importer reopens the vulnerable item: SecurityInsight still sees the finding (the same rule as the SQL connector). |
| Security recommendation (not a CVE) | A Defender for Cloud recommendation on vm-demo-app01, still reported: u_finding_type = azure-recommendation, u_vulnerability = its assessment key, u_title = its name. | Identity finding | IDENTITY-SPN-001 on sp-demo-payroll-sync, new this run: u_finding_type = identity, on an identity CI (u_class_hint = identity). | A vulnerable item on the identity's CI (an Entra identity class), through a third-party entry -- or not imported, if your transform leaves identities out. |

| Vulnerability closed: Out of scope | CVE-2099-10005 on SRV-APP01 is still on the machine, but outside the scope this target receives: Closed, u_close_reason = Out of scope. | Closed with a close code that is NOT fixed. |
| Vulnerability closed: Duplicate | CVE-2099-10006 on LAPTOP-0142 had two records -- one under the asset's own id, one under its CI key. The OLDER one keeps the finding (now under the CI key); the newer one is Closed with u_close_reason = Duplicate and keeps the id it ends under. Both channels carry the close (REST: a close row). | Closed with a close code that is NOT fixed; the other record stays open. Coalescing on u_source_record_id keeps each item on its own record. |
| Vulnerability re-keyed (one CI key) | The kept record of CVE-2099-10006 moved from the asset's own id to the CI key (the vulnerability rows used to carry the asset id). Same record, same u_source_record_id, history kept -- not a new finding, not a close. | With coalesce on u_source_record_id the vulnerable item is updated in place and now resolves its CI. |
| Vulnerability held (asset not seen) | CVE-2099-10007 on LAPTOP-0077: the asset is not seen, so SecurityInsight cannot tell whether it was fixed -- the record stays Open (REST: u_action = held, the why in u_si_reason). | Nothing changes on the vulnerable item. |
| Vulnerability closed: Asset retired | CVE-2099-10008 on SRV-OLD02: the asset was retired after the grace period of a server, so its open vulnerabilities close with u_close_reason = AssetRetired. If the asset comes back they reopen. The close ceiling still guards a mass retirement. | Closed with a close code that is NOT fixed (for example "retired" / "not applicable"). |
| Held batch | On 2026-10-04 Defender answered only in part: 3 of the 5 active CIs of the previous batch were missing (60%, above the connector's limit). The batch was recorded as held and never shown; the import views kept showing the complete batch of 2026-10-03. | Your import reads the previous complete batch again; nothing is retired by a partial collection. |
| Import Set push: a complete batch | Each output's push is one batch. Before its first row SecurityInsight writes a writing row to the staging status table (u_si_staging_status); every CI and vulnerability row carries the batch id (u_si_batch_id); after the last row it writes a complete row with the same id, the planned and accepted counts and the import sets. | Your importer starts when the complete row arrives and imports exactly the rows with that u_si_batch_id. |
| Import Set push: a failed batch | A call was refused part-way: the end row says failed, with u_sent_rows, u_failed_rows and u_reason. The rows that did land carry the batch id. | Your importer does not import the batch. Its rows come again in a later batch; the last complete batch stays what ServiceNow holds. |
| Import Set push: a held batch | SecurityInsight stopped the push before it sent anything (for example the ServiceNow check found a column missing in the staging table): writing, then held with u_si_reason; no data row was sent. | Nothing to import. Your importer waits for the next complete batch. |

## Approval checklist

- [ ] SecurityInsight is registered as a choice on cmdb_ci.discovery_source.
- [ ] Every staging column is a u_ column of the view (or of the Import Set rows), unchanged. The two channels carry the same columns; every Import Set row adds the contract's envelope (u_action, u_si_batch_id, u_si_cleared, u_si_reason, u_si_replaces), and a vulnerability row adds u_row_hash and u_source_run.
- [ ] Dates are UTC: a datetime in the SQL views, yyyy-MM-dd HH:mm:ss in the Import Set rows (ServiceNow's own format, no date-format setting needed).
- [ ] The transform map uses IRE with discovery source SecurityInsight; your own identification rules stay first, u_si_correlation_id (if used) is the last identifier entry.
- [ ] SecurityInsight is authoritative only for the security attributes (tier, tier reason, exposure, last seen, source run); it is the lowest-priority source for everything else.
- [ ] An asset-keyed row (u_id_source = asset: no ledger id yet) does not create a CI.
- [ ] Proposed CIs (vProposedCi) are a report: nothing is created from them unless your rules allow creation for that class.
- [ ] Key-values and relations with u_state = removed are removed or flagged, never left as present.
- [ ] A CI with u_si_state = not-seen or retired is handled by your rules (a flag, a task, install_status) -- never deleted because SecurityInsight no longer sees it.
- [ ] Vulnerable items coalesce on u_source_record_id when present, else on u_si_correlation_id + u_vulnerability, so a re-sent or re-keyed row never creates a second item.
- [ ] A finding that is not a CVE (u_finding_type other than cve) maps to a third-party entry with u_vulnerability as its id and u_title as its name.
- [ ] Only u_close_reason = Remediated closes as fixed; Out of scope, Duplicate, AssetRetired and NoLongerMonitored map to non-fix close codes.
- [ ] Records SecurityInsight did not send (u_source other than SecurityInsight) are never touched by the transform.
- [ ] The data source filters u_changed_at > the last import (delta), and imports only after the newest batch is complete.
- [ ] A held batch changes nothing in ServiceNow.
- [ ] Import Set push: the staging status table exists (default u_si_staging_status, extends Import Set Row, every column of rest/u_si_staging_status.json), and both data staging tables have u_si_batch_id.
- [ ] Import Set push: your importer imports a batch only once its complete row exists in the staging status table, every complete batch once, oldest first; failed, held and writing batches are never imported.
- [ ] Retention: the Import Set cleanup keeps at least the rows of the two newest complete batches of each output.

## The staging status table (Import Set push)

When SecurityInsight pushes rows through the Import Set API, each output's push is one batch, and a third import set table says when a batch is complete: the staging status table, `u_si_staging_status` (label *SecurityInsight staging status*). Create it like the two data staging tables -- extending Import Set Row (`sys_import_set_row`), with exactly these column names -- and give both data staging tables the column `u_si_batch_id` (string, 100).

| Column | Label | Type | Length | Meaning |
|---|---|---|---|---|
| `u_si_batch_id` | Batch id | string | 100 | The batch: <SecurityInsight run id>:<output>. The same value is on every data row of the batch (u_si_batch_id) and on both status rows of the batch. |
| `u_si_output` | Output | string | 40 | Which output the batch belongs to: servicenow-ci (configuration items) or servicenow-vulnerable-item (vulnerable items). |
| `u_si_state` | State | string | 16 | writing (the batch has started), complete (every row was accepted: import it), failed (some rows were not accepted: do not import) or held (stopped before or while sending: do not import); or feedback (information only: the import result SecurityInsight read back for a complete batch -- never a batch state). |
| `u_si_connector` | Connector | string | 100 | The SecurityInsight connector that sent the batch. |
| `u_si_target_table` | Target staging table | string | 80 | The staging table the batch's data rows were sent to. |
| `u_si_source_run` | Source run | string | 100 | The SecurityInsight run that sent the batch. |
| `u_si_started_at` | Started at | glide_date_time | 40 | When the batch started (UTC, yyyy-MM-dd HH:mm:ss). |
| `u_si_finished_at` | Finished at | glide_date_time | 40 | When the batch ended (UTC). Only on the end row. |
| `u_si_batch_time` | Batch time | glide_date_time | 40 | When the batch became complete (UTC). Only on a complete row -- the same meaning as u_batch_time in the SQL hand-off. |
| `u_si_planned_rows` | Planned rows | integer | 40 | How many data rows the batch sends. On the writing row when it is known before sending; always on the end row. |
| `u_si_sent_rows` | Sent rows | integer | 40 | How many data rows ServiceNow accepted. Only on the end row. |
| `u_si_failed_rows` | Failed rows | integer | 40 | How many planned data rows were not accepted (or not sent). Only on the end row; 0 on a complete row. |
| `u_si_import_set_ids` | Import sets | string | 4000 | The import sets ServiceNow made for the batch's data rows, comma separated (for diagnosis -- select a batch's rows by u_si_batch_id). A long list ends with (+N more). |
| `u_si_reason` | Reason | string | 1000 | Why the batch ended as it did, in plain words. |
| `u_si_version` | SecurityInsight version | string | 64 | The SecurityInsight version that sent the batch. |
| `u_si_contract_version` | Contract version | string | 16 | The version of the SecurityInsight data contract the batch follows. Columns are only ever added; a rename or a removal comes with a new version. |
| `u_si_mode` | Mode | string | 16 | live (a normal sync), resync (an Admin asked for every record again: import it like live) or test (a test batch: never import it). |
| `u_si_new_rows` | New rows | integer | 40 | Rows of the batch with u_action = new. Only on the end row. |
| `u_si_update_rows` | Update rows | integer | 40 | Rows with u_action = update. Only on the end row. |
| `u_si_close_rows` | Close rows | integer | 40 | Rows with u_action = close. Only on the end row. |
| `u_si_reopen_rows` | Reopen rows | integer | 40 | Rows with u_action = reopen. Only on the end row. |
| `u_si_held_rows` | Held rows | integer | 40 | Records SecurityInsight holds in this batch (u_action = held, plus first-time records it does not send yet). Only on the end row. |
| `u_si_out_of_scope_rows` | Out of scope rows | integer | 40 | Rows with u_action = out_of_scope. Only on the end row. |
| `u_si_import_inserted` | Import: inserted | integer | 40 | Your import's result for the batch, as SecurityInsight read it back: rows inserted. Only on a feedback row. |
| `u_si_import_updated` | Import: updated | integer | 40 | Rows updated. Only on a feedback row. |
| `u_si_import_ignored` | Import: ignored | integer | 40 | Rows ignored, including rows your IRE onBefore script handed over and ignored. Only on a feedback row. |
| `u_si_import_skipped` | Import: skipped | integer | 40 | Rows skipped. Only on a feedback row. |
| `u_si_import_errors` | Import: errors | integer | 40 | Rows in error. More than 0 raises a SecurityInsight issue. Only on a feedback row. |
| `u_si_import_pending` | Import: pending | integer | 40 | Rows not transformed yet when SecurityInsight read the result (read again at the next sync). Only on a feedback row. |

Every batch has exactly two rows in `u_si_staging_status`, with the same `u_si_batch_id`: `writing` before the first data row, then `complete`, `failed` or `held` after the last. **Import a batch only once its `complete` row exists: the data rows whose `u_si_batch_id` is that batch's id.** `rest/u_si_staging_status.json` shows the rows of a complete, a failed and a held batch.

## When SecurityInsight no longer sees an asset

The CI row carries `u_si_state`: `active` while the asset is seen, `not-seen` once it has not been seen for 8 days, and `retired` once it has not been seen for longer than the grace period of its kind -- 30 days by default, set per kind in SecurityInsight (client PCs, servers, service principals, users, Azure VMs, other Azure resources) -- or an Admin retired it early. The row stays in the hand-off with its last `u_last_seen`, and its `u_changed_at` moves when the state changes, so a delta import picks it up. The open vulnerabilities of a retired asset close with `u_close_reason` = `AssetRetired` (not a fix); if the asset is seen again it is `active` again and its findings reopen. What a not-seen or retired CI means in your CMDB is your transform's decision. SecurityInsight never retires or deletes a CI in ServiceNow, and never touches records it did not send.
